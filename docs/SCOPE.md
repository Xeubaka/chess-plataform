**Environment note (found 2026-09-10, device-bridge/local runs only):** git operations across the polyrepo submodules here (`frontend`, `services/*`) can leave a stale `.git/index.lock` (and sometimes `HEAD.lock` / `objects/*/tmp_obj_*` / `objects/maintenance.lock`) behind after essentially *any* git command — this sandbox can create files but is not permitted to delete them, so git's own end-of-command cleanup silently fails. The next git command in that repo then fails with "Unable to create '.git/index.lock': File exists." Fix: before (and after) each git command in a submodule, `mv` any `*.lock` / `tmp_obj_*` file under `.git/` out of the way (e.g. append `.stale.$(date +%s)`) rather than deleting it — `mv` works, `rm` does not. This is unrelated to actual lock contention; no other process is running. Also: only the `frontend` repo has a local git identity (`user.name`/`user.email`) configured; other submodules and the main repo don't, so a first commit in a fresh submodule needs `git config user.name/user.email` set locally (matching `frontend`'s) before it will succeed.
